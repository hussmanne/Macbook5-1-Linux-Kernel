# Independent review — 2026-10-29

Scope: the whole repository at `7ef0554` (66 files), the three custom kernel
tiers, their build/verification chain, the installers, and the acceptance
claims. This document separates three kinds of statement:

- **[measured]** — I executed it in a clean environment during this review.
- **[inferred]** — read from the pinned upstream source, the patch, or the
  repository's own scripts.
- **[estimate]** — my judgement, with the reasoning shown. These are
  probabilities, not guarantees.

Nothing here replaces a physical boot. The point of the review is that the
repository currently optimises *breadth* (more tiers, more gates, more docs)
while the single decisive measurement — one boot of one tier on the actual
laptop — has still never happened.

---

## 1. Bottom line

1. **[measured] You do not have three kernels. You have one kernel with two
   switch-flips.** Resolved from the pinned source with the repo's own scripts:
   Daily vs BORE differs by exactly two configuration symbols
   (`CONFIG_SCHED_BORE=y`, `CONFIG_MIN_BASE_SLICE_NS=2000000`); Daily vs Lab
   differs by exactly two (`CONFIG_HZ_250=y`, `CONFIG_HZ=250`); and **legacy v2
   vs Daily differs by nothing at all except `LOCALVERSION`** — same source,
   same patch set (none), byte-identical configuration. Same installer, same
   Broadcom flow. The repository ships three distinct *builds*, two of which
   are one config symbol apart, and it calls four of them tiers.
2. **[inferred] The BORE tier's "safe" control arm is not a control.**
   `kernel.sched_bore=0` turns off the burst heuristic, but the build still
   carries BORE's compile-time base-slice and tunable-scaling constants. A
   "BORE off" boot is measurably *not* the Daily scheduler: request size
   2 ms vs 1.4 ms, slice-protection window 2 ms vs 0.7 ms, tunable scaling
   `NONE` vs `LOG`. Any Daily-vs-BORE(0) difference therefore proves nothing.
3. **[measured] A large part of your "what's out" story is decoration.**
   44 disable toggles; **33 were already off in `x86_64_defconfig`** and change
   nothing. Six more only close a WLAN vendor menu with no driver behind it.
   Five or six actually remove code. Meanwhile ~15 genuinely useless subsystems
   inherited from the defconfig are still built in (virtio/9p guest stack,
   eight unused wired NIC drivers, PCCARD/YENTA, NUMA, SELinux, KEXEC,
   `SCHEDSTATS`, `PM_DEBUG`, `KALLSYMS_ALL`, DRM_VIRTIO_GPU …).
4. **[measured, one verification step left] There is very likely no visible
   kernel console on any tier.** `FB` is off
   in the defconfig; `DRM_FBDEV_EMULATION` defaults to `FB` and
   `FRAMEBUFFER_CONSOLE` defaults to `DRM_FBDEV_EMULATION`, so both resolve to
   `n`, and `FB_EFI`/`SIMPLEDRM` are off too. `VGA_CONSOLE=y` cannot drive a
   panel that EFI/GOP has already put in graphics mode. On a kernel whose
   known behaviour includes Nouveau DRM warnings, a failed X session gives you
   a black screen and no text VT. This is the cheapest fix in the repository
   (`CONFIG_FRAMEBUFFER_CONSOLE=y`, `CONFIG_DRM_FBDEV_EMULATION=y`).
5. **[inferred] The irreversible security choice is a false dilemma.**
   `CONFIG_CPU_MITIGATIONS=n` was justified with "cannot be reversed with a
   boot flag". `CONFIG_CPU_MITIGATIONS=y` + `mitigations=off` on the command
   line is reversible, costs code size and almost nothing at runtime
   (alternatives patch the mitigation sites out), and preserves your ability
   to *measure* the mitigation cost — which you currently cannot, because the
   option is baked into every tier.
6. **[estimate] Boot probability is high; "works as a daily driver" probability
   is moderate, and the dominant risks are not in the kernel.** The kernel is
   a small delta from v1, which booted. The new, untested things are the
   install plumbing (hand-built GRUB paths, hostonly dracut), the proprietary
   Broadcom rebuild, and the absence of any visible console when one of them
   fails.
7. **[inferred] The most valuable work is free and unstarted.** `preempt=full`
   vs `lazy`, `sched_autogroup_enabled`, `scaling_governor`
   (`schedutil`/`ondemand`/`conservative`/`powersave`), EEVDF tunables, zram
   algorithm, MGLRU knobs, PCIe ASPM, USB autosuspend — all runtime-switchable,
   all measurable without a single rebuild, and none of them is in the plan.

## 2. What the three kernels actually are

**[measured]** I downloaded the pinned upstream archive and verified it byte for
byte against `source.lock`
(`sha256 = 1af6d999…384295`, 262 MiB, matches). I then ran the repository's own
pipeline in this order — `x86_64_defconfig` → `scripts/configure.sh` →
resolution equivalent to `make olddefconfig` → `scripts/audit-config.sh` — for
all four tiers. All four audits pass, and the locked BORE patch
(`sha256 = 33ec2b48…1e632`, 1393 lines, 14 files) applies cleanly with
`git apply --check --whitespace=error`.

| Tier | Source | Code patch | Configuration difference from Daily | Local version |
|---|---|---|---|---|
| legacy v2 | `21a7f44f` | none | **none** (identical config; only `LOCALVERSION`) | `-mbp51-extreme-g21a7f44f-v2` |
| Daily | `21a7f44f` | none | — (reference) | `-mbp51-daily-g21a7f44f-v1` |
| BORE | `21a7f44f` | 1393-line port | `SCHED_BORE=y`, `MIN_BASE_SLICE_NS=2000000` | `-mbp51-bore-g21a7f44f-bore7.0.0-r1` |
| Lab | `21a7f44f` | none (config-only) | `HZ_250=y`, `HZ=250` | `-mbp51-lab-g21a7f44f-lab-hz250-r1` |

Deltas were produced by resolving each tier from the same pristine tree and
diffing the resulting `CONFIG_*` lines; only the `LOCALVERSION` string differs
in the legacy case.

Consequences that the documentation does not state plainly:

- **Correlated risk.** One source pin, one base config, one installer, one
  Broadcom patcher. A source-level regression, a config mistake, a dracut
  mistake or a GRUB path mistake takes out all three entries simultaneously.
  Three custom entries give you *experiment separation*, not *risk
  separation*. The only genuinely independent kernel on the machine is
  `linux-lts`.
- **Legacy v2 is a duplicate build, not a fourth experiment.** It has its own
  pacman base, its own Broadcom package (`mbp51-broadcom-wl` vs
  `-daily`), its own installer path and its own `LOCALVERSION`, but produces
  the same kernel and the same modules as Daily. Installing both puts two
  identical kernels with two module trees and two Wi-Fi builds on the same SSD
  and adds a fifth GRUB entry to the comparison matrix. Keep the v1 boot entry
  you already have proof for if you like, but stop rebuilding a second copy of
  Daily and calling it legacy.
- **The naming oversells the content.** "Extreme Hardware Lab" is a 250 Hz tick.
  `patches/lab.lock` says `LAB_PROFILE_KIND=config-only`; there is no voltage,
  GPU-rail, firmware or platform code anywhere in the tree. The README's
  "performance- and power-oriented … three tiers" framing, and
  `THREE-TIER-MULTIBOOT.md`'s "Tier 3 — Extreme Hardware Lab … experimental
  codebase for voltage", describe a plan, not the artifact you can download.
  `DAILY-INDEPENDENT.md` and `EXTREME-LAB-BOOT-TEST.md` are more honest; the
  front page is not.
- **The "most reliable" tier rests on the least stable base.** Daily is pinned
  to a merge-window development snapshot. A tier whose contract is "the
  trustworthy daily baseline" should be pinned to something with a stable
  release history, and the development pin should belong to the experimental
  tier. This is the sharpest contradiction in the repository: the same
  `source.lock` is used for the conservative tier and the throwaway ones, so
  the conservative tier can never be more stable than the bleeding edge.

## 3. Where the reasoning breaks

### 3.1 "Three independent tiers" (false independence)

*Claim:* Tier 1/2/3 are independent kernels, so you can always fall back.
*Reality:* they share source, base config, packaging, installer and Wi-Fi
module path. Independence requires either a different source pin or a
different config lineage; you have neither. Only `linux-lts` is independent.
*Fix:* describe the tiers as *experiment classes over one base build*, and stop
counting them as redundancy in the risk discussion.

### 3.2 "`sched_bore=0` gives EEVDF behaviour" (unfalsifiable control)

*Claim* (`THREE-TIER-MULTIBOOT.md`, `BORE-INDEPENDENT.md`): BORE compiles with a
runtime switch, `0` = EEVDF-style.
*Reality* [inferred from the patch]: under `CONFIG_SCHED_BORE` the patch
replaces, unconditionally:

| Constant | Daily (EEVDF) | BORE build, even with `sched_bore=0` |
|---|---|---|
| `sysctl_sched_tunable_scaling` | `LOG` (×2 on 2 CPUs) | `NONE` (×1) |
| request size `sysctl_sched_base_slice` | 1.4 ms | 2.0 ms (`nsecs_per_tick × ceil(2 ms / 1 ms)`) |
| `set_protect_slice()` window | 0.7 ms (normalized) | 2.0 ms |
| `sched_update_scaling()` | present | compiled out |

So the "control arm" already changes the scheduler. `BORE-INDEPENDENT.md` half
admits this in one sentence ("not claimed to be byte-identical"), but
`THREE-TIER-MULTIBOOT.md` still sells `0` as EEVDF-style, and the test matrix
still uses it as the baseline.
*Fix:* either (a) port the patch so the EEVDF constants are kept when
`sched_bore=0` (the tunable-scaling and base-slice hunks are separable —
`update_sysctl()` can consult the static key), or (b) run three arms with the
control quantified: Daily, BORE(`sched_min_base_slice=1000000`) to get the
closest achievable slice match, BORE(1). Note the quantisation: at HZ=1000 the
BORE formula can only produce 1, 2, 3 … ms, so a 1.4 ms match is impossible.

### 3.3 "HZ=250 is a power experiment" (mechanism mismatch)

*Claim:* Lab's first profile is a power-oriented tick experiment.
*Reality:* with `NO_HZ_IDLE` the periodic tick is already stopped in idle; the
tick frequency does not change idle residency in any measurable way. What HZ
changes is *preemption granularity under load* and timer coalescing. With
`PREEMPT_LAZY` the tick **is** the preemption point, so dropping 1000 → 250 Hz
predicts up to ~4 ms of extra wakeup-to-run delay, i.e. a likely *regression*
in interactivity and ~0 W of power difference.
*Fix:* stop spending a boot entry on HZ. If you want to quantify it, do it as
one arm of a scheduler matrix, not as "Tier 3". If you want a *power* result,
test `scaling_governor` (see §7), which on a Penryn with slow ACPI P-state
transitions plausibly moves watts, and is a one-line runtime change.

### 3.4 The irreversible mitigation trade-off (false dilemma)

*Claim* (README, ENGINEERING, INSTALL): `CONFIG_CPU_MITIGATIONS=n` is a
deliberate, irreversible performance decision.
*Reality:* the reversible alternative — `CONFIG_CPU_MITIGATIONS=y` plus
`mitigations=off` on the kernel command line — disables the same mitigations at
boot, is worth doing precisely because it is reversible, and lets you A/B the
cost with two GRUB entries against one binary. The remaining difference is
code size and a handful of alternative-patched sites, which is noise next to
KPTI being off either way.
*Why it matters here:* on a Penryn the applicable mitigations are Meltdown
(PTI), Spectre v1/v2 and SSB; PTI is the expensive one and `mitigations=off`
removes it. You already get the performance. You do not have to give up the
ability to turn it back on — and you should, because "browser JavaScript can
read kernel memory" is a real risk on a daily driver.
*Fix:* ship `=y` with `mitigations=off` in the custom GRUB entries, keep one
`mitigations=auto` entry for measurement, and keep the LTS entry as the secure
fallback.

### 3.5 "Hardware family trimming" / "small footprint" (misallocated effort)

**[measured]** classification of every toggle in `scripts/configure.sh` against
the resolved `x86_64_defconfig`:

| Toggle class | Count | Actually changed | Comment |
|---|---|---|---|
| `no …` (disable) | 44 | 5–6 | 33 were already `n`; 6 are WLAN vendor menu gates with no driver behind them; `ZRAM_BACKEND_LZO` only matters because ZRAM is enabled later |
| `yes …` (enable) | 69 | 19 | the other 50 were already `y` and only re-state the default |
| `mod …` (module) | 25 | 25 | 10 × y→m, 15 × n→m — all real |

Disabling `INFINIBAND`, `THUNDERBOLT`, `USB4`, `HYPERV`, `XEN`, `KVM`,
`DRM_AMDGPU`, `DRM_RADEON`, `DRM_XE`, `DRM_AST`, `B43`, `BRCMSMAC`,
`BRCMFMAC`, `ZSWAP`, `NO_HZ_FULL`, `KASAN`, `KCSAN`, `UBSAN`, `LOCKDEP`,
`KGDB`, `KDB`, `FAULT_INJECTION`, `GCOV_KERNEL`, `FUNCTION_TRACER` and friends
removes **nothing** — those symbols were already off. It documents intent, and
intent documentation is fine, but it is not trimming, and the README presents it
as trimming.

Meanwhile these are still in every build [measured]:

| Still built in | Why it should not be |
|---|---|
| `VIRTIO_BLK/NET/PCI/INPUT/CONSOLE`, `SCSI_VIRTIO`, `NET_9P`, `NET_9P_VIRTIO`, `9P_FS` | bare metal, no hypervisor, no 9p mount plan |
| `E1000`, `E1000E`, `R8169`, `TIGON3`, `NET_TULIP`, `SKY2`, `8139TOO`, `E100`, `MACINTOSH_DRIVERS` | eight wired NICs for a machine with one forcedeth port |
| `PCCARD`, `YENTA` | the 15" unibody has ExpressCard/34, not PCMCIA |
| `NUMA` | one node, two cores |
| `SECURITY_SELINUX`, `KEXEC`, `AGP`, `DRM_VIRTIO_GPU` | unused on an Arch/EndeavourOS desktop |
| `SCHEDSTATS`, `PM_DEBUG`, `PM_TRACE_RTC`, `BLK_DEV_IO_TRACE`, `KALLSYMS_ALL`, `DEBUG_ENTRY`, `DEBUG_WX`, `DEBUG_STACK_USAGE`, `PROVIDE_OHCI1394_DMA_INIT` | the docs promise "no unexpected kernel debug instrumentation"; these are scheduler hot-path counters and debug machinery |
| `X86_CHECK_BIOS_CORRUPTION`, `IA32_EMULATION`, `HPET`, `KEXEC` | defensible keeps, listed for completeness |

`SCHEDSTATS` is the only one of these that sits in a hot path you care about
(`enqueue`/`dequeue`/context switch accounting). The rest are size, boot time
and attack surface. **The honest position is that pruning does not buy battery**
— and the engineering doc says so — so this is a size/hygiene issue, not a
reason to keep spending effort on toggles that were already off.

### 3.6 "CI green ⇒ the artifact is safe to install" (unreachable gate)

The repository has built an impressive provenance chain: pinned SHA + measured
archive digest, tier-locked local versions, package-content assertions,
Broadcom compile/vermagic checks, portable checksum verification. **[measured]**
the digest and patch hash verify exactly, and all four config audits pass.

And none of it can answer the only question that matters, because every gate
runs in a container on hardware that is not the laptop. The docs say this
repeatedly and honestly. The fallacy is procedural, not textual: **the
verification effort is placed where it cannot produce the answer**, while the
free decisive experiment (boot stock LTS, run `scripts/compare-kernels.sh`,
establish the battery baseline) has not been done and is not blocking anything.

### 3.7 Priority inversion

[Temporal evidence from the handoff] Three installers, four build workflows,
a Broadcom compatibility matrix, a hardware survey tool, a benchmark harness,
an ISO remixer, a USB remixer, ~15 documents — and zero physical boots of v2 or
any tier. If the next three changes are "more tiers", the project will keep
adding confidence machinery without ever converting it into knowledge.

### 3.8 Unfalsifiable diagnostics

- `ACPI_SBS=m` is added "as a diagnostic". The `sbs` driver binds to the ACPI
  SBS device; it cannot create a battery that firmware does not expose. There is
  no stated hypothesis, no acceptance test and no way for the result to be
  "wrong". (It is harmless; it is also not evidence.)
- The "battery mystery" has an obvious unforced hypothesis never written down:
  a **dead or disconnected battery**. A 2008 battery, `PNP0C0A` present but no
  `BAT*`, UPower degraded — all three are consistent with "no battery present"
  and none of them requires a kernel defect. The decisive test is one LTS boot,
  not a new tier.

### 3.9 "Tier 1 is the trustworthy baseline" (asserted reliability)

Reliability is a measurement, not a position in a table. The only custom kernel
with a physical boot is the *legacy* one, which is also the one with missing
audio and no battery. Daily's ordering (`LTS > Daily > BORE > Lab`) is a
reasonable prior about distance-from-upstream, but it is presented as a
contract. Say "closest to upstream defaults and least modified", and let the
first boot decide.

### 3.10 Acceptance criteria with no measurable inputs

The policy is "every optimisation: baseline, changed measurement, KEEP /
REVERT / NEEDS EVIDENCE". The measurement plumbing cannot yet produce the
inputs:

- **Power**: `append_sample()` sums `/sys/class/power_supply/BAT*/power_now`.
  With no `BAT*` (v1's observed state) that is an empty glob → the column reads
  `0`, indistinguishable from "0 µW". The documentation knows an AC wattmeter
  may be needed; the harness does not say so.
- **Temperature**: reads `/sys/class/thermal/thermal_zone*/temp`. This machine's
  sensors are SMC (`applesmc`) and, if you enabled it, `coretemp`; neither
  guarantees a thermal zone. Column likely `0`.
- **Config identity**: `config_sha256` comes from `/proc/config.gz`, then
  `/boot/config-$(uname -r)`. Both are absent here (`CONFIG_IKCONFIG` is off
  [measured], and Arch's `pacman-pkg` does not install `/boot/config-*`), so
  every comparison prints `config_sha256=unavailable` and the "config must be
  reviewed before comparing" guard silently passes. (Patched in this branch:
  the harness now falls back to `/usr/lib/modules/$(uname -r)/build/.config`,
  which the headers package always installs.)

Result: the KEEP/REVERT protocol has three columns that are structurally zero
or missing. Fix the instruments before running the experiment.

## 5. Probability of booting and working

Basis [estimate]: v1 booted on this machine with a config that differs from
Daily only by the recovered-feature symbols (`USER_NS`, `MEMCG`, `PSI`, ACLs,
Realtek codecs, `ACPI_SBS`) — none of which can affect early boot. Everything
new and risky is outside the kernel: GRUB entry synthesis, hostonly dracut,
the Broadcom rebuild, and the missing console that hides failures.

| Tier | Boots to a shell | Reaches graphical login | Usable as a daily driver | Dominant residual risk |
|---|---|---|---|---|
| `linux-lts` (stock) | ~99 % | ~99 % | ~95 % | distro-tested baseline |
| legacy v1 (already proven) | ~99 % | ~99 % | ~40 % | no audio, no battery, no userspace namespaces |
| **Daily** | **90–95 %** | **80–85 %** | **~70 %** | installer/GRUB path, hostonly dracut, no console if X fails |
| **BORE** | 88–93 % | 75–82 % | ~60 % | out-of-tree scheduler port on a dev tree; control arm invalid |
| **Lab (HZ 250)** | 90–95 % | 80–85 % | ~65 % (but no expected gain) | same plumbing; the change itself is low-risk to boot and probably a latency regression |

How to read those numbers: they are *not* a statement that the kernels are
fragile. They are a statement that 3 of the top 4 failure classes live in the
install/qualification path, which no CI job exercises.

**Ordered failure modes** (highest probability first):

1. **X/Nouveau comes up degraded or not at all, and you cannot see why**
   (no console). Mitigation: enable `FRAMEBUFFER_CONSOLE` +
   `DRM_FBDEV_EMULATION`, and know `Ctrl-Alt-F2` will actually show text.
2. **GRUB entry points at the wrong path.** `activate-daily-kernel.sh`
   hand-builds `$subvol/boot/mbp51/$subdir/vmlinuz` from `findmnt` output and
   only checks that `/boot` has the same *filesystem UUID* as `/`. If `/boot`
   ever lives in a different Btrfs subvolume, the entry is silently wrong.
   The EndeavourOS installer does this properly with `grub-mkrelpath` /
   `grub-probe`. Mitigation: use the same method everywhere; verify the
   subvolume too.
3. **Broadcom build blocks the whole install.** `--install` refuses to add a
   boot entry until `wl.ko` builds *and* is vermagic-correct *and* resolves to
   the private path. That is a good safety property for Wi-Fi and a bad one for
   kernel qualification: the most fragile step gates the kernel test.
   Mitigation: `--no-wifi` / `--entry-only` mode, install the entry first, add
   `wl` afterwards.
4. **Battery/power measurements remain impossible**, so no tier can ever be
   declared better. Mitigation: resolve `BAT*` (or accept AC-side measurement
   and write it into the harness).
5. **`SCHED_BORE` instability** (rare): the port touches `fork`, `exit`,
   `futex`, `core.c`, `fair.c`. Boot-time risk is low; long-run risk is not
   zero.

What would move Daily from ~90 % to ~98 %: the console, `grub-mkrelpath`, a
`--no-wifi` path, and the post-boot assertion script added in this branch,
which names the acceptance item that failed instead of leaving you with "it
didn't work".

## 6. Concrete defects (small, safe to fix now)

1. **`.github/workflows/build-daily.yml` does not rebuild when `source.lock`
   changes.** BORE and Lab both list `source.lock` in `paths:`; Daily does not
   (nor `scripts/check-kconfig.sh`). A source bump silently leaves the Daily
   artifact stale — the installer then rejects it, so it fails safe, but you
   lose the tier without a signal.
2. **Release string is hard-coded `7.3.0` in 15 places across 8 files**
   (`install/*.sh`, `compat/broadcom/*`, `scripts/test-verify-artifacts.sh`,
   `iso/remaster-with-kernel.sh`, `patch-broadcom-wl.py`). A source bump must
   touch all of them or fail in five different ways. Derive it once (e.g.
   `SOURCE_KERNEL_VERSION` in `source.lock`) and reference it.
3. **`scripts/benchmark/common.sh` could not establish config identity**
   (§3.10). Fixed in this branch: it now falls back to
   `/usr/lib/modules/$(uname -r)/build/.config`, which the headers package
   always installs.
4. **Power/temperature columns silently read `0` when the source is absent.**
   This branch adds `power_now_source=` / `thermal_source=` metadata keys and a
   hwmon temperature fallback; the CSV value itself still reads `0`, so read
   the metadata before trusting a wattage.
5. **`scripts/hardware-report.sh` prints an empty battery section** when no
   `BAT*` exists; the absence is exactly the evidence you want recorded.
6. **`powertop --auto-tune` is global with no exceptions**, while
   `ENGINEERING.md` and `LOCAL-MODEL-HANDOFF.md` both promise "narrowly scoped
   exceptions" once regressions appear. Right now the runtime unit contradicts
   the policy document; make the exception mechanism explicit (a unit drop-in
   or a documented `--auto-tune` re-application list) before invoking it on the
   laptop.
7. **Three near-duplicate installers** (`activate-custom-kernel.sh`,
   `activate-endeavouros-kernel.sh`, `activate-daily-kernel.sh`) already
   diverge in how they build the GRUB path and which initramfs modes they use.
   One implementation with a `--layout` flag removes a whole class of
   "which script did I run?" bugs.
8. **`README.md`'s layout tree is stale** (it lists ~12 of 66 files and omits
   `benchmark/`, `tools/`, `iso/`, most docs and workflows). Cosmetic, but it is
   the map a new reader trusts.

## 7. What I would add (prioritised)

### P0 — before any further tier work

1. **Boot stock LTS and record the baseline.** `scripts/compare-kernels.sh`,
   `scripts/hardware-report.sh`, `bash scripts/postboot-check.sh` (added in this
   branch). This settles the battery question, gives you real watt/temperature
   data, and is the only comparison that can prove a regression.
2. **Config revision v2 (needs a `-v2` suffix so provenance stays honest):**
   ```text
   yes FRAMEBUFFER_CONSOLE          # visible text console
   yes DRM_FBDEV_EMULATION          # fbcon over nouveau
   yes FB_EFI                       # early boot console before KMS
   yes IKCONFIG
   yes IKCONFIG_PROC                # /proc/config.gz for the harness
   mod SENSORS_CORETEMP             # per-core Penryn temperatures
   yes CPU_MITIGATIONS              # + mitigations=off on the cmdline
   ```
   and, optionally, remove the dead weight listed in §3.5 (`VIRTIO_*`, `NET_9P`,
   `9P_FS`, unused NICs, `PCCARD`/`YENTA`, `SCHEDSTATS`, `PM_DEBUG`,
   `BLK_DEV_IO_TRACE`). Add the first six to `audit-config.sh` so they cannot
   regress.
3. **`scripts/postboot-check.sh`** — an executable acceptance gate (added in
   this branch). Roughly twenty PASS/WARN/FAIL lines covering console, config
   provenance, PSI/MEMCG/ACL, ALSA cards, Realtek codec, `BAT*`/`power_now`,
   `wl` path and vermagic, gmux backlight, DRM nodes, zram lz4, applesmc,
   thermal/fan sensors, failed units and kernel warning counts. Run it on LTS,
   then on each tier; keep the output and treat FAIL as "do not promote".
4. **Fix the BORE control** (§3.2) or drop BORE until it has one. A tier whose
   A/B cannot be interpreted costs a boot entry, an installer, a Broadcom
   package and a workflow.

### P1 — free measurements, no rebuild

Run these as a 2×2 matrix on **one** kernel (Daily), changing one variable per
boot, recording `postboot-check.sh` + `ui-load.sh` + a wattmeter or `energy_now`
delta:

| Knob | How | What it can show |
|---|---|---|
| `preempt=lazy` vs `preempt=full` (`PREEMPT_DYNAMIC`) | boot param / `/sys/kernel/debug/sched/preempt` | the real interactivity lever on this CPU; may make HZ irrelevant |
| `kernel.sched_autogroup_enabled` 0/1 | runtime sysctl | affects every UI-latency measurement you take later |
| `scaling_governor` `schedutil` / `ondemand` / `conservative` / `powersave` | sysfs | plausible multi-watt and latency effect on Penryn (slow ACPI P-state transitions); the *actual* power experiment Lab should run |
| EEVDF `sched_base_slice`, `sched_migration_cost`, `sched_wakeup_granularity` | sysfs | smaller slices → responsiveness vs throughput on 2 cores |
| `zram` algorithm `lz4` vs `zstd:1` | zram-generator + swapoff/swapon | memory pressure cost |
| `/sys/kernel/debug/lru_gen` max_seq / min_ttl_ms | debugfs | MGLRU aggressiveness |
| PCIe ASPM (`pcie_aspm.policy=performance\|powersave`) | boot param | only after `lspci -vv` shows supported states |
| USB autosuspend per device | `/sys/bus/usb/devices/*/power/control` | interacts badly with the Broadcom USB BT; use as the documented exception list |

Any of these that shows a repeatable effect is worth a category "KEEP"; none of
them requires the other two kernel packages to exist.

### P2 — later, only with data

- BORE port that keeps EEVDF constants when the static key is off; then a
  three-arm run (Daily, BORE slice-matched, BORE(1)).
- `b43`+`ssb`+`bcma` as modules in **one** tier (Lab) as a Wi-Fi fallback that
  does not depend on the proprietary blob. Costs ~1 MB, removes a single point
  of failure from qualification.
- `HID_APPLEIR` if the remote is wanted; `SENSORS_CORETEMP` for undervolt work.
- Linux `stable` tree as the pin for Daily and the dev snapshot only for
  experiments (this is the change that would actually make "Tier 1 is the
  reliable one" true).
- Hibernation: keep it on LTS and stop treating its absence as a decision worth
  defending.

## 8. Suggested sequence (and what "done" means)

1. Boot LTS. Capture `compare-kernels.sh` + `hardware-report.sh` +
   `postboot-check.sh`. **Done when** `BAT*` presence/absence is explained and
   at least one temperature and one power signal is non-zero (or the absence is
   documented with an external wattmeter plan).
2. Apply config v2 (§7.2) with a `-v2` suffix, rebuild Daily only, install it
   with the `--plan` output reviewed line by line, and boot it. **Done when**
   `postboot-check.sh` reports no FAIL and you can read the failure text on
   screen if it does not.
3. Runtime knob matrix on Daily (§7.1 table). **Done when** each row is
   KEEP/REVERT/NEEDS EVIDENCE with numbers.
4. Only then: BORE with a valid control, or Lab redefined around governor/P-state
   instead of HZ.

Everything after step 2 is cheap. Steps 1 and 2 are the ones the repository has
been deferring.

## 10. Addendum — configuration revision `c2`, and what "three kernels" means

### 10.1 The tier question, answered plainly

Yes: three separate kernels are built — three pacman packages, three module
trees, three boot entries, three private Broadcom modules. That part is real.

The correction from §1 stands but needs stating precisely: the three tiers
share **one** hardware profile. Stripping and optimising happen once, in
`scripts/configure.sh`, and apply identically to all three. Only the
experiment symbol differs.

That is the correct architecture, not a defect. Three *different* hardware
configurations would mean a failure in one tier teaches you nothing about the
others, and every hardware fix would have to be made three times. What was
actually wrong is the quality of the shared profile: it was
`x86_64_defconfig` plus 80 toggles, of which most changed nothing and a
handful of required capabilities were missing entirely. `c2` fixes the profile.

### 10.2 Four capability gaps the first pass missed

These were only found while implementing `c2`, and they matter more than most
of what §3 lists:

| Symbol | Was | Consequence on a real EndeavourOS desktop |
|---|---|---|
| `NF_TABLES` (+`INET`,`COMPAT`,`NAT`) | `n` | Arch ships `iptables-nft` and firewalld speaks nf_tables. **No working firewall** on a laptop using other people's Wi-Fi. Legacy `ip_tables` alone is not what any EndeavourOS front-end drives. |
| `FUSE_FS` | `n` | AppImages, Flatpak, sshfs and any libfuse tool fail to mount. |
| `OVERLAY_FS` | `n` | Flatpak runtimes, podman/docker overlay2 and `systemd-sysext` fail. |
| `BPF_SYSCALL` / `CGROUP_BPF` | `n` | systemd cgroup features degrade; `bpftrace` unavailable, which removes a profiling tool the tier comparison needs. |

Also added: `SECURITY_APPARMOR` (the documented rule is to preserve
non-mitigation security features) and `DM_CRYPT` (one module of insurance
against a later LUKS decision).

Each of these was off in `x86_64_defconfig`, and none of them was covered by
any existing gate. That is the concrete cost of a defconfig-derived profile:
the audit can only check what someone remembered to list.

### 10.3 Two traps worth recording

- `scripts/config --module` on a **bool** writes `CONFIG_X=m`, which Kconfig
  drops to `n`. `NF_TABLES_INET` and `NF_TABLES_IPV4/IPV6` are bools; using
  `mod` produced a kernel with no `inet` table family while the audit passed,
  because nothing required it yet. The audit now does.
- `audit-config.sh` used `grep … && return` inside functions under `set -e`;
  on the success path that returns 1 and kills the whole script. Both helpers
  are now explicit `if` blocks, and a negative test confirms the audit fails
  when a required symbol is wrong.

### 10.4 Measured effect

Resolved from the pinned source for all four tiers; `audit-config.sh` passes
for each.

| Metric | `c1` | `c2` |
|---|---|---|
| `=y` symbols | 1622 | 1572 |
| `=m` symbols | 93 | 122 |
| Built symbols turned off | — | 90 |
| Unbuilt symbols turned on | — | 70 |

`c2` removes more code than it adds. **Symbol counts only** — no size or
performance claim is made, because nothing here was compiled. CI produces the
real numbers and the audit fails loudly if the profile stops resolving.

### 10.5 Still unproven, stated explicitly

- **No compile.** Every claim above is Kconfig resolution plus `bash -n` and
  the repository's own static tests. That is exactly the gap §3.6 describes.
- **No boot.** `postboot-check.sh` has never run on the machine.
- **kconfiglib is not `make olddefconfig`.** It cannot parse this tree's
  `transitional`, bare `modules`, or `depends on X if Y` constructs, so offline
  verification ran against a patched throwaway copy. `SCHED_SMT` was withdrawn
  rather than shipped on unproven resolution.
